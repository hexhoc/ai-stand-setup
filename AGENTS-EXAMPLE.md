# Project instructions

## Структура проекта

- `<configAlias>/src` — основная конфигурация `<base-name>`.
- `<configAlias>.<ExactExtensionName>/src` — прикладное расширение `<ExactExtensionName>`.
- `<configAlias>.YAxUnit/src` — тестовый движок; не изменять его исходники без отдельной задачи.
- `<configAlias>.tests/src` — расширение для тестов проекта.
- XML-исходники созданы Конфигуратором 1С, это не EDT-проект.
- `<configAlias>` — короткое имя из строчных ASCII-букв, цифр и дефисов; имя расширения после точки должно точно совпадать с метаданным свойством `Name`.

## Границы изменений

- Основная конфигурация: `<read-only либо разрешено изменение>`.

- Не удалять, не сбрасывать и не перезаписывать несвязанные пользовательские изменения.

## Обязательный порядок анализа

1. Определить объект метаданных, модуль и контекст выполнения.
2. Прочитать минимально необходимый XML объекта.
3. Для расширения сопоставить объект с основной конфигурацией.
4. Найти вызовы и платформенные точки входа.
5. Выполнить минимальное корректное изменение.
6. Запустить профильную проверку skill и диагностику BSL Language Server.

## YAxUnit: восстановление и запуск тестов

- Этот раздел применяется, только если проект использует YAxUnit и расширение `tests`.
- Тестовая база определяется только по точному локальному alias `yaxunit-test`; не подменять её базой по умолчанию, текущей веткой, нечётким именем или похожим alias.
- Alias `yaxunit-test` должен присутствовать ровно у одной базы. При отсутствии предложить разработчику назначить dev/test базу после подтверждения, что это не production; при дублировании остановиться.
- Осознанное назначение alias `yaxunit-test` разрешает без повторного вопроса восстанавливать только расширения `YAxUnit` и `tests` в этой локальной базе. Разрешение не распространяется на данные, основную конфигурацию и другие расширения.
- Исходники восстановления: `<configAlias>.YAxUnit/src` и `<configAlias>.tests/src`.
- Перед каждым запуском получать фактический список расширений через `db-cfe-admin list`.
- Проверять, что YAxUnit и tests существуют и активны; у YAxUnit должны быть отключены безопасный режим и защита от опасных действий.
- При отсутствии расширений загружать их через project skills строго в порядке YAxUnit → tests, применять через `db-update` и проверять через `db-cfe-admin check`.
- Перед запуском синхронизировать изменённые исходники `tests` с тестовой базой.
- Для запуска использовать `/yaxunit-test [фильтр]` или тот же workflow вручную.
- Каждый запуск создавать в `build/yaxunit/runs/<timestamp>-<short-id>/` новый уникальный каталог с `config.json`, `exit-code.txt`, `report.xml` и `tests.log`.
- Запускать 1С через `db-run` с `CParam=RunUnitTests=<absolute-config-path>`.
- `db-run` возвращает управление до завершения тестов; его код завершения не является результатом YAxUnit.
- Успех подтверждается только свежим `exit-code.txt` со значением `0`, корректным свежим jUnit без `failures`/`errors` и ожидаемым ненулевым числом тестов.
- При таймауте анализировать `tests.log` и процесс текущего запуска; не запускать второй прогон поверх первого и не завершать чужие процессы 1С.
- Официальный формат конфигурации: <https://bia-technologies.github.io/yaxunit/docs/getting-started/run/configuration>.

## BSL MCP

- Использовать прямой MCP BSL Language Server с именем `bsl-language-server`, запускаемый командой `bsl-language-server.exe mcp --protocol stdio`.
- Для обзора модуля использовать `document_symbols`, для диагностики — `analyze_file`.
- Для поиска определений, ссылок и вызовов использовать `definition`, `find_references` и `call_hierarchy`.
- Для платформенных типов и глобального контекста использовать `type_info`, `type_at_position`, `global_member_info` и `global_member_search`.
- Перед рефакторингом проверять ссылки и иерархию вызовов для изменяемого символа.
- После изменения BSL запускать `analyze_file` для каждого изменённого модуля.
- Позиции `line` и `character` в MCP нумеруются с нуля.
- Если BSL MCP недоступен, использовать точечный поиск по файлам и явно сообщить об ограничении.

## XML и расширения

- Основная конфигурация определяется отсутствием `ConfigurationExtensionPurpose`; расширение — наличием этого точного элемента.
- Не путать `ConfigurationExtensionPurpose` с `ConfigurationExtensionCompatibilityMode`.
- При работе с расширением проверять `ObjectBelonging`, `ExtendedConfigurationObject`, `xr:PropertyState`, `NamePrefix` и настройки сопоставления.
- Для `&Перед`, `&После`, `&Вместо` и `&ИзменениеИКонтроль` сравнивать сигнатуру и тело с точной версией основной конфигурации.
- Отсутствие текстового вызова не означает, что метод не используется: учитывать подписки, команды, формы, регламентные задания, HTTP/Web-сервисы и другие точки входа платформы.

## Чтение и изменение файлов

- Не читать большие BSL/XML-файлы целиком без необходимости.
- Сначала найти точный символ или XML-узел, затем читать узкий контекст.
- Не переформатировать большие XML-файлы целиком.
- Не изменять окончания строк и несвязанные участки файлов.
- При добавлении или удалении объекта согласованно изменять объект, его каталог и `Configuration.xml`.
- Не выполнять `git reset --hard`, `git clean`, `git checkout --` и другие команды, способные удалить пользовательские изменения.

## Проверка

- После изменения метаданных запускать соответствующий `*-validate` skill.
- После изменения формы проверять форму и её модуль.
- После изменения расширения запускать `cfe-validate` с основной конфигурацией.
- После изменения BSL получать диагностики BSL Language Server для каждого изменённого модуля.
- Изменения в базу загружать только по запросу пользователя, кроме восстановления YAxUnit/tests в однозначно разрешённой локальной базе с alias `yaxunit-test`.
- Выполнять проектные команды проверки: `<project-specific-validation-commands>`.
