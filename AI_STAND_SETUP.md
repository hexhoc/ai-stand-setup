# Инструкция для AI-агента: подготовка XML-проекта 1С к агентской разработке

## Назначение

Эта инструкция предназначена для OpenCode, работающего в Windows с проектом 1С:Предприятие, исходники которого хранятся в XML-выгрузке Конфигуратора, а не в формате EDT.

Результат подготовки:

- подключены проектные skills для разработки на 1С и работы с БСП;
- установлены project rules и связанные commands для разработки на 1С;
- найдены или выгружены XML-исходники основной конфигурации и выбранных расширений;
- при согласии пользователя подключены YAxUnit и отдельное расширение `tests`;
- настроены Git и MCP для BSL Language Server;
- создан или актуализирован `AGENTS.md` на основе канонического шаблона `AGENTS-EXAMPLE.md` из комплекта; сам шаблон в целевой проект не копируется;
- каждый этап можно безопасно запустить повторно.

Все команды выполняй из корня подготавливаемого проекта, если явно не указано иное.

## 1. Обязательные принципы

### 1.1. Идемпотентность

Для каждого шага соблюдай порядок:

1. Проверь фактическое состояние.
2. Сравни его с требуемым.
3. Если требуемое состояние уже достигнуто — ничего не изменяй и отметь шаг как `пропущен`.
4. Если требуется обновление — меняй только относящуюся к шагу часть.
5. Проверь результат.

Не считай наличие каталога достаточным признаком успешной установки. Проверяй содержимое, remote Git, XML-свойства и состояние MCP.

### 1.2. Сохранность пользовательских данных

- Не перезаписывай существующие файлы целиком, если можно изменить отдельный блок.
- Не удаляй и не пересоздавай чужие каталоги и настройки.
- Не выполняй `git reset --hard`, `git clean`, `git checkout --` и аналогичные команды сброса.
- Клонируй вспомогательные репозитории только во временные каталоги. Удаляй в `finally` только checkout и родительский временный каталог, созданные текущим запуском; существующие пользовательские checkout не изменяй и не удаляй.
- Перед заменой непустого каталога XML-выгрузки обязательно запроси подтверждение.
- Перед загрузкой конфигурации или расширения в информационную базу получи подтверждение пользователя. Одно подтверждение может покрывать заранее перечисленную последовательность операций.
- Исключение допустимо только для автоматического восстановления `YAxUnit` и `tests` в локальной базе, которой разработчик после подтверждения назначил точный alias `yaxunit-test` в игнорируемом `.v8-project.json`. Для другой или неоднозначно определённой базы подтверждение обязательно; production-база запрещена.
- Не помещай пароли, токены и другие секреты в отслеживаемые Git файлы.

### 1.3. Отчётность

Для каждого этапа используй один из статусов:

- `готово` — создано впервые;
- `обновлено` — существующий компонент актуализирован;
- `пропущено` — требуемое состояние уже достигнуто или пользователь отказался от необязательного этапа;
- `ожидает пользователя` — требуется ручное действие или решение;
- `ошибка` — этап не завершён.

В конце выдай компактную таблицу: этап, статус, результат, требуемое ручное действие.

## 3. Установка и обновление project skills

### 3.1. Важное правило об `cc-1c-skills`

Репозиторий `cc-1c-skills` — не просто справочная документация. Он содержит готовые skills и исполняемые PowerShell/Python-скрипты для полного цикла работы с XML-проектами 1С, в том числе:

| Задача | Skill |
|---|---|
| Реестр информационных баз | `db-list` |
| Выгрузка основной конфигурации и расширений в XML | `db-dump-xml` |
| Загрузка XML в базу | `db-load-xml` |
| Загрузка CF/CFE | `db-load-cf` |
| Применение изменений к базе | `db-update` |
| Список, проверка и свойства расширений в базе | `db-cfe-admin` |
| Запуск 1С:Предприятия с параметром `/C` | `db-run` |
| Создание нового расширения | `cfe-init` |
| Проверка расширения | `cfe-validate` |
| Проверка основной конфигурации | `cf-validate` |
| Анализ и изменение объектов, форм, ролей и СКД | соответствующие `meta-*`, `form-*`, `role-*`, `skd-*` |

После установки используй эти skills и их штатные скрипты. Не заменяй их самописными вызовами `1cv8.exe`, если нужный skill существует и работоспособен.

Если skills установлены во время текущей сессии и ещё не появились в инструменте `skill`, не заявляй, что необходимых средств нет. Прочитай `.opencode/skills/<skill>/SKILL.md`, затем используй указанный там скрипт из `.opencode/skills/<skill>/scripts/`. Для автоматического обнаружения новых skills в последующей разработке предложи открыть новую сессию OpenCode.

### 3.2. `cc-1c-skills`

Устанавливай skills из нового временного checkout. Не клонируй репозиторий в целевой проект и не используй существующий пользовательский checkout. Сохрани commit до удаления, чтобы включить его в итоговый отчёт.

Безопасная последовательность:

```powershell
$ProjectRoot = (Get-Location).Path
$TempRoot = Join-Path ([System.IO.Path]::GetTempPath()) ("dev-agent-" + [guid]::NewGuid().ToString("N"))
$Checkout = Join-Path $TempRoot "cc-1c-skills"
$TempRootCreatedBySetup = $false
$SkillsCommit = $null

try {
    New-Item -ItemType Directory -Path $TempRoot -ErrorAction Stop | Out-Null
    $TempRootCreatedBySetup = $true

    & git clone "https://github.com/Nikolay-Shirokov/cc-1c-skills.git" $Checkout
    if ($LASTEXITCODE -ne 0) {
        throw "Не удалось клонировать cc-1c-skills."
    }

    $SkillsCommit = (& git -C $Checkout rev-parse HEAD).Trim()
    if ($LASTEXITCODE -ne 0 -or -not $SkillsCommit) {
        throw "Не удалось определить commit cc-1c-skills."
    }

    $SwitchScript = Join-Path $Checkout "scripts\switch.py"
    & python $SwitchScript opencode --project-dir $ProjectRoot
    if ($LASTEXITCODE -ne 0) {
        throw "Не удалось установить cc-1c-skills."
    }
}
finally {
    if ($TempRootCreatedBySetup -and (Test-Path -LiteralPath $TempRoot)) {
        Remove-Item -LiteralPath $TempRoot -Recurse -Force -ErrorAction Stop
    }
}
```

После очистки проверь:

- временный каталог текущего запуска отсутствует;
- `.opencode/skills/.cc-1c-skills.json` существует;
- `.opencode/skills/db-dump-xml/SKILL.md` и `.opencode/skills/cfe-init/SKILL.md` существуют;
- скрипты, упомянутые в установленных skills, доступны внутри `.opencode/skills`.

Если очистка временного checkout завершилась ошибкой, не скрывай её: отметь установку как незавершённую и сообщи точный оставшийся путь. Не удаляй одноимённые или ранее существовавшие каталоги.

Повторный запуск `switch.py` является штатным способом обновления и не должен удалять сторонние skills, перечисление которых отсутствует в манифесте `cc-1c-skills`.

### 3.3. Skill для БСП

Skill БСП также устанавливается **в текущий проект**, в `.opencode/skills/bsp`.

Не перезаписывай существующий пользовательский `install.ps1`. Если файл с таким именем уже есть в корне, используй другое временное имя или запроси решение. Удаляй только тот установщик, который скачал текущий запуск.

Базовая последовательность:

```powershell
irm https://raw.githubusercontent.com/brake71/1c-ssl-skills/main/install.ps1 -OutFile install.ps1
.\install.ps1 -Agent OpenCode -Target ./.opencode/skills
Remove-Item .\install.ps1
```

> В PowerShell фактическая команда запуска должна быть `./install.ps1` или `.\install.ps1`. Не допускай появления управляющих символов при копировании команды.

Предпочтительный безопасный вариант:

```powershell
$Installer = Join-Path (Get-Location) "install.ps1"
$DownloadedBySetup = $false
try {
    if (Test-Path -LiteralPath $Installer) {
        throw "Файл install.ps1 уже существует; нельзя безопасно его перезаписать."
    }
    Invoke-RestMethod "https://raw.githubusercontent.com/brake71/1c-ssl-skills/main/install.ps1" -OutFile $Installer
    $DownloadedBySetup = $true
    & $Installer -Agent OpenCode -Target (Join-Path (Get-Location) ".opencode\skills")
}
finally {
    if ($DownloadedBySetup -and (Test-Path -LiteralPath $Installer)) {
        Remove-Item -LiteralPath $Installer
    }
}
```

Проверь `.opencode/skills/bsp/SKILL.md`. Установщик атомарно обновляет только каталог `bsp`; соседние skills должны сохраниться.

Учти в дальнейших правилах: справочники этого skill подтверждают API БСП 3.1.11. Для другой версии БСП сигнатуры и существование методов проверяй по XML-исходникам соответствующей версии основной конфигурации.

### 3.4. Комплект правил и команд

После установки `cc-1c-skills` и `bsp` установи комплект из каталога `content`, поставляемого вместе с этой инструкцией.

#### Поиск источника комплекта

Определи каталог, содержащий исходный `AI_STAND_SETUP.md`. Рядом с ним должны находиться:

```text
content/manifest.json
content/rules/
content/commands/
```

Если инструкция была скопирована отдельно и `content/manifest.json` рядом отсутствует, запроси путь к checkout `dev-agent`. Не скачивай другой ruleset и не реконструируй файлы по памяти.

#### Целевые каталоги OpenCode V2

| Источник | Целевой проект |
|---|---|
| `content/rules/*.md` | `.opencode/rules/*.md` |
| `content/commands/*.md` | `.opencode/commands/*.md` |

Используй plural-каталог OpenCode V2 `commands/`. `.opencode/rules` является стабильным проектным каталогом: OpenCode не загружает его автоматически, правила читаются по условным маршрутам из `AGENTS.md` и команд. Не добавляй `.opencode/rules/*.md` в `instructions`: это безусловно загрузит весь набор вместо выбора правил по задаче.

#### Идемпотентное обновление

Состояние установки храни в `.opencode/.dev-agent-content.json`: версия manifest, целевые пути и SHA-256 установленного содержимого. Файл не содержит секретов и хранится в Git.

Для каждого файла:

1. Новый путь — создать.
2. Существующий путь отсутствует в предыдущем состоянии установки — считать пользовательским; при совпадении SHA-256 зарегистрировать как управляемый, иначе не перезаписывать без решения пользователя.
3. Текущий SHA-256 совпадает с предыдущим установленным — обновить из комплекта.
4. Управляемый путь изменён пользователем — не перезаписывать; показать различия и запросить решение.
5. Файл исчез из нового manifest — удалить только если он был управляемым и не изменён пользователем.
6. Не трогать сторонние файлы в тех же каталогах.

Копируй во временный файл в том же каталоге, проверяй hash и затем заменяй целевой файл. Повторный запуск на актуальной версии не должен менять рабочее дерево.

После завершения подготовки предложи начать новую сессию OpenCode: новая сессия гарантированно перечитает проектные инструкции и skills.

## 4. Поиск и классификация XML-исходников

### 4.1. Поиск

Рекурсивно найди `Configuration.xml`, исключив как минимум:

- `.git`;
- `.opencode`;
- `tools`;
- `build`;
- временные каталоги.

Не классифицируй файл по одному только имени или имени родительской папки. Разбери XML с учётом namespace.

### 4.2. Классификация

Найди в свойствах конфигурации точный XML-элемент `ConfigurationExtensionPurpose`:

- элемента нет — основная конфигурация;
- элемент есть — расширение конфигурации.

Не путай его с `ConfigurationExtensionCompatibilityMode`: этот элемент может присутствовать и в основной конфигурации.

Для каждого найденного файла определи:

- значение точного свойства `Name` конфигурации или расширения;
- `Version`, если оно заполнено;
- каталог `src`, содержащий `Configuration.xml`;
- корневой каталог компонента — родитель `src`.

Выведи пользователю таблицу найденных компонентов. Если найдено несколько основных конфигураций, не выбирай одну самостоятельно — запроси выбор.

### 4.3. Короткое имя основной конфигурации

Для новой выгрузки основной конфигурации запроси или предложи короткое имя `configAlias`.

Требования:

- только строчные латинские ASCII-буквы, цифры и `-`;
- шаблон: `^[a-z][a-z0-9-]*$`;
- имя должно быть коротким и отражать назначение конфигурации.

Примеры:

| Конфигурация | Короткое имя |
|---|---|
| Зарплата и управление персоналом | `zup` |
| Бухгалтерия предприятия | `acc` |
| Управление торговлей | `trade` |
| 1С:ERP | `erp` |

В примере `acc` все символы должны быть латинскими. Не допускай визуально похожих кириллических букв.

Получай подтверждение пользователя до создания каталогов. Если основная конфигурация уже существует в корректной структуре, используй имя её корневого каталога. Не переименовывай существующую структуру автоматически.

### 4.4. Структура каталогов

Основная конфигурация:

```text
<корень проекта>/<configAlias>/src/Configuration.xml
```

Пример:

```text
zup/src/Configuration.xml
```

Каждое расширение:

```text
<корень проекта>/<configAlias>.<ExtensionName>/src/Configuration.xml
```

`ExtensionName` — точное значение метаданного свойства `<Name>`, а не синоним. Сохраняй регистр и кириллицу.

Пример:

```text
zup.РасширениеЗУП/src/Configuration.xml
```

Если целевой каталог:

- отсутствует или пуст — его можно использовать;
- содержит соответствующую XML-выгрузку того же объекта — не создавай заново, реши отдельно, требуется ли обновление;
- непустой, но не содержит ожидаемую выгрузку — остановись и запроси другой путь;
- содержит выгрузку другого объекта — не перезаписывай.

## 5. Получение XML из информационной базы

### 5.1. Когда запрашивать базу

Запроси параметры информационной базы, если:

- основная конфигурация не найдена;
- пользователь подтвердил, что в проекте должны быть прикладные расширения, но их XML не найден;
- выбран необязательный этап YAxUnit;

Поддерживай:

- файловую базу: путь;
- серверную базу: сервер и имя базы;
- имя пользователя и пароль, если нужны;
- путь к нужной версии платформы 1С, если автоопределение неоднозначно;
- реквизиты хранилища конфигурации, если база подключена к нему.

Используй формат и алгоритм из `.opencode/skills/db-list/SKILL.md`. `.v8-project.json` — локальный реестр информационных баз проекта, который используют все `db-*` skills, а также skills сборки и запуска 1С. Он должен быть исключён из Git, поскольку содержит индивидуальные пути и может содержать секреты.

Перед любой операцией с базой проверь наличие и корректность `.v8-project.json`. Если файл отсутствует, не передавай задачу дальше и не угадывай базу: восстанови реестр по разделу 5.2, затем вернись к исходной операции.

### 5.2. Шаблон `.v8-project.json`

Формируй шаблон после определения фактических путей основной конфигурации и расширений. Пример для файловой базы с тестовым контуром:

```json
{
  "v8path": "<LOCAL_1C_BIN_PATH>",
  "databases": [
    {
      "id": "dev-local",
      "name": "Локальная база разработки",
      "type": "file",
      "path": "<LOCAL_INFOBASE_PATH>",
      "aliases": [
        "dev",
        "yaxunit-test"
      ],
      "configSrc": "<configAlias>/src",
      "extensions": [
        {
          "name": "YAxUnit",
          "src": "<configAlias>.YAxUnit/src"
        },
        {
          "name": "tests",
          "src": "<configAlias>.tests/src"
        }
      ]
    }
  ],
  "default": "dev-local"
}
```

Требования к шаблону:

- подставь реальные общие относительные пути XML проекта;
- перечисли остальные расширения проекта с их точными `<Name>` и `src`;
- если тестовый контур не выбран, не добавляй `YAxUnit`, `tests` и alias `yaxunit-test`;
- оставь placeholders только для локального подключения и пути к платформе;
- не добавляй в шаблон реальные значения `user`, `password`, пути файловых баз, server/ref или реквизиты хранилища из рабочего файла;
- при повторном запуске актуализируй только общую структуру и пути, сохраняя отсутствие секретов.

Если `.v8-project.json` удалён или отсутствует в новом клоне:

1. Загрузи skill `db-list` или прочитай `.opencode/skills/db-list/SKILL.md`.
2. Спроси разработчика:
   - путь к базе;
   - пользователя и пароль, если нужны;
   - локальный путь к нужной платформе, если автоопределение неоднозначно;
3. Если нужен запуск YAxUnit, отдельно подтверди, что выбранная база является dev/test, не production, и после подтверждения добавь ей точный alias `yaxunit-test`.
4. Удали или замени все placeholders. Не выполняй DB-команды с незаполненным шаблоном.
5. Создай `.v8-project.json` атомарно, проверь JSON, уникальность `databases[].id` и aliases.
6. Выполни безопасную проверку подключения и только затем продолжи исходную DB-операцию.

Если разработчик не предоставил локальные реквизиты, продолжай доступный анализ XML, но отметь выгрузку, загрузку и тесты как `ожидает пользователя` с указанием причины.

### 5.3. Выгрузка основной конфигурации

Если основной конфигурации нет:

1. Согласуй `configAlias`.
2. Целевой каталог установи в `<configAlias>/src`.
3. Прочитай `.opencode/skills/db-dump-xml/SKILL.md`.
4. Выполни полную выгрузку штатным скриптом `db-dump-xml` с `-Mode Full`.
5. Проверь код возврата и лог Конфигуратора.
6. Повторно разбери `<configAlias>/src/Configuration.xml` и убедись, что это основная конфигурация.
7. Выполни доступную проверку через `cf-validate`.

Не выгружай полностью поверх существующей XML-выгрузки без подтверждения: полная выгрузка может изменить большое число файлов из-за версии формата платформы.

### 5.4. Выгрузка расширений

Если прикладные расширения в проекте не найдены:

1. Спроси, должны ли они присутствовать. Отсутствие расширений может быть корректным состоянием.
2. Получи список расширений базы через `db-cfe-admin list`.
3. Покажи список пользователю и попроси выбрать расширения для Git. Не выгружай автоматически все служебные расширения.
4. Для каждого выбранного расширения создай отдельный путь:

   ```text
   <configAlias>.<точное имя расширения>/src
   ```

5. Выполни `db-dump-xml -Mode Full -Extension "<Name>"` в соответствующий каталог.
6. Проверь, что в XML присутствует `ConfigurationExtensionPurpose`, а `<Name>` совпадает с выбранным расширением.
7. Выполни `cfe-validate` с путём к основной конфигурации.

Если расширения уже найдены, не запрашивай базу только ради повторной выгрузки. Сначала спроси, требуется ли их обновить.

## 6. Необязательный тестовый контур YAxUnit

Перед этим разделом задай один явный вопрос: нужно ли подключить к проекту YAxUnit и создать расширение `tests`? При отрицательном ответе пропусти раздел целиком.

При подключении тестового контура у обоих расширений — `YAxUnit` и `tests` — должны быть отключены свойства «Безопасный режим», «Защита от опасных действий» и «Использовать основные роли для всех пользователей».

### 6.1. Получение YAxUnit

1. Получи последний стабильный, не draft и не prerelease релиз через GitHub API:

   ```text
   https://api.github.com/repos/bia-technologies/yaxunit/releases/latest
   ```

2. Выбери asset с именем `YAxUnit-<version>.cfe`, не `Smoke-<version>.cfe`.
3. Проверь требования релиза к платформе и совместимость с целевой базой.
4. Скачай файл в игнорируемый каталог `build/yaxunit/`.
5. Если GitHub API публикует `digest`, проверь SHA-256 скачанного файла.

### 6.2. Проверка существующего YAxUnit

Проверь независимо:

- есть ли `YAxUnit` в информационной базе;
- есть ли XML-выгрузка `<configAlias>.YAxUnit/src/Configuration.xml`;
- какая версия установлена или выгружена.

Правила:

- в базе и проекте уже находится нужная версия — пропусти установку и выгрузку;
- в базе есть более старая версия — покажи сравнение версий и запроси подтверждение обновления;
- в базе версия новее загруженной с GitHub — не понижай её;
- YAxUnit есть в базе, но XML нет — только выгрузи его;
- XML есть, но расширения нет в базе — предложи загрузить XML через `db-load-xml -Extension YAxUnit`;
- ничего нет — установи скачанный CFE после подтверждения.

### 6.3. Установка в базу

Для новой установки или согласованного обновления:

1. Используй `.opencode/skills/db-load-cf/SKILL.md` и загрузи CFE как расширение `YAxUnit`.
2. Проверь точное имя расширения через `db-cfe-admin list`.
3. Сними у YAxUnit:
   - безопасный режим;
   - защиту от опасных действий;
   - использование основных ролей для всех пользователей.
4. Используй `db-cfe-admin set-properties`, если целевая база и установленный `ibcmd` это поддерживают.
5. Если свойства нельзя изменить автоматически, остановись и попроси пользователя снять их вручную в Конфигураторе. Не объявляй установку завершённой до подтверждения.
6. Примени расширение через `db-update -Extension YAxUnit`.
7. Проверь применимость и синтаксис через `db-cfe-admin check`.

### 6.4. XML-выгрузка YAxUnit

Выгрузи расширение в:

```text
<configAlias>.YAxUnit/src
```

Используй `db-dump-xml -Mode Full -Extension YAxUnit`, затем `cfe-validate`.

### 6.5. Расширение `tests`

Точное метаданное имя расширения — `tests`.

Целевой каталог:

```text
<configAlias>.tests/src
```

Если корректное расширение уже существует, не пересоздавай его.

Для нового расширения:

1. Прочитай `.opencode/skills/cfe-init/SKILL.md`.
2. Создай расширение с параметрами:
   - `Name`: `tests`;
   - `Synonym`: `Тесты`;
   - `NamePrefix`: `tests_`;
   - `Purpose`: `AddOn`;
   - `ConfigPath`: путь к основной конфигурации;
   - `OutputDir`: `<configAlias>.tests/src`.
3. Проверь расширение через `cfe-validate`.
4. Предложи загрузить его в базу через `db-load-xml -Extension tests`.
5. После загрузки проверь точное имя расширения через `db-cfe-admin list` и через `db-cfe-admin set-properties` отключи у `tests` безопасный режим, защиту от опасных действий и использование основных ролей для всех пользователей.
6. Если свойства нельзя изменить автоматически, остановись и попроси пользователя снять их вручную в Конфигураторе. Не объявляй подключение завершённым до подтверждения.
7. Примени расширение через `db-update -Extension tests`.
8. Проверь применимость и синтаксис.

Не добавляй тесты, включая демонстрационные, без явного запроса пользователя. Если пользователь не указал состав и количество тестов либо методы, которые должны быть покрыты, сначала уточни эти требования; не выбирай их самостоятельно.

### 6.6. Локальное назначение тестовой базы

Отслеживаемые файлы проекта не должны содержать конкретный `id`, путь, server/ref или пользователя базы. Каждый разработчик назначает собственную тестовую базу только в игнорируемом `.v8-project.json`.

Чтобы агент мог восстановить расширения после замены локальной базы из бэкапа:

1. Если `.v8-project.json` отсутствует, восстанови его по разделу 5.2.
2. Покажи базы из `.v8-project.json` без паролей.
3. Попроси выбрать ровно одну dev/test базу для автоматических тестов.
4. Получи явное подтверждение, что это не production-база и не база, в которой запрещено изменение конфигурации.
5. После подтверждения добавь выбранной записи точный зарезервированный alias `yaxunit-test`. Само осознанное назначение этого alias означает локальное разрешение автоматически восстанавливать в этой базе только расширения `YAxUnit` и `tests`.
6. Удали alias `yaxunit-test` из других записей, но только после подтверждения пользователя, если он там уже присутствует. В результате alias должен разрешаться ровно в одну базу.
7. Идемпотентно добавь или актуализируй в выбранной записи сопоставления исходников, не дублируя элементы `extensions`:

   ```json
   {
     "extensions": [
       { "name": "YAxUnit", "src": "<configAlias>.YAxUnit/src" },
       { "name": "tests", "src": "<configAlias>.tests/src" }
     ]
   }
   ```

   Это фрагмент записи базы, а не замена всего массива: сохрани остальные расширения и поля.

Не записывай выбранный `id`, другие локальные aliases подключения, путь файловой базы, server/ref, пользователя или пароль в отслеживаемые файлы. Зарезервированное имя alias `yaxunit-test` указывай там только как общее правило разрешения базы, без локальной записи, которой оно назначено.

Если тестовая база не выбрана, автоматическое восстановление и запуск тестов не настраивай: отметь этап как `ожидает пользователя`.

### 6.7. Обязательный preflight перед тестами

Перед **каждым** запуском YAxUnit агент обязан проверить фактическое состояние назначенной базы. Наличие XML в Git не означает, что расширения сохранились в базе после восстановления бэкапа.

Алгоритм:

1. Проверь `.v8-project.json`; при отсутствии восстанови его по разделу 5.2.
2. Найди базу строго по точному alias `yaxunit-test`. Не используй ветку Git, `default`, нечёткое имя или похожий alias как замену.
3. Alias должен присутствовать ровно у одной базы. Если он отсутствует — предложи локально назначить dev/test базу по разделу 6.6; если найден у нескольких — остановись и попроси исправить неоднозначность.
4. Получи список расширений выбранной базы через `db-cfe-admin list`.
5. Проверь `YAxUnit`:
   - расширение существует;
   - активно;
   - безопасный режим отключён;
   - защита от опасных действий отключена;
   - использование основных ролей для всех пользователей отключено.
6. Проверь `tests`:
   - расширение существует;
   - активно;
   - безопасный режим отключён;
   - защита от опасных действий отключена;
   - использование основных ролей для всех пользователей отключено.
7. Если у существующего расширения `YAxUnit` или `tests` включено хотя бы одно из трёх указанных свойств, отключи его через `db-cfe-admin set-properties`.
8. Если `YAxUnit` отсутствует, восстанови его полной загрузкой из `<configAlias>.YAxUnit/src` через `db-load-xml -Extension YAxUnit`, отключи все три указанных свойства и примени через `db-update -Extension YAxUnit`.
9. Если XML YAxUnit отсутствует или невалиден, не импровизируй: восстанови исходники по разделу 6.1–6.4 либо сообщи блокер.
10. Если `tests` отсутствует, после YAxUnit загрузи `<configAlias>.tests/src` через `db-load-xml -Extension tests`, отключи все три указанных свойства и примени через `db-update -Extension tests`.
11. Если текущая задача изменила исходники `tests`, синхронизируй изменения с базой перед запуском. Для исчезнувшего расширения всегда используй полную загрузку; для существующего допускается корректная частичная загрузка через `db-load-xml`, если skill однозначно сформировал полный список зависимых файлов.
12. Выполни `db-cfe-admin check` для `YAxUnit` и `tests` как минимум с проверками применимости и синтаксиса.
13. Только после успешного preflight переходи к запуску тестов.

Порядок восстановления неизменен: сначала `YAxUnit`, затем `tests`. Не загружай их параллельно.

Если автоматическое изменение свойств YAxUnit или tests недоступно для выбранного типа базы, запроси ручное отключение безопасного режима, защиты от опасных действий и использования основных ролей для всех пользователей у соответствующего расширения. Не запускай тесты в заведомо неправильном режиме.

Если применимость нарушена из-за несовпадения основной конфигурации с XML-исходниками проекта, остановись и сообщи расхождение. Не отключай проверку применимости ради продолжения.

### 6.8. Конфигурация отдельного запуска

Не создавай постоянный отслеживаемый `tests/yaxunit.json`. Каждый прогон должен получать новый уникальный каталог:

```text
build/yaxunit/runs/<timestamp>-<short-id>/
├── config.json
├── exit-code.txt
├── report.xml
└── tests.log
```

Каталог `build/` уже исключён из Git. Уникальный каталог не позволяет принять артефакты старого прогона за новые.

Генерируй `config.json` JSON-сериализатором, а не конкатенацией строк. Используй абсолютные пути и следующую структуру:

```json
{
  "filter": {
    "extensions": ["tests"]
  },
  "reportFormat": "jUnit",
  "reportPath": "<absolute-path>/report.xml",
  "exitCode": "<absolute-path>/exit-code.txt",
  "closeAfterTests": true,
  "showReport": false,
  "workspacePath": "<absolute-project-root>",
  "logging": {
    "file": "<absolute-path>/tests.log",
    "console": true,
    "level": "debug"
  }
}
```

Источник формата: <https://bia-technologies.github.io/yaxunit/docs/getting-started/run/configuration>.

Правила фильтрации:

- без аргументов — все тесты расширения `tests`;
- имя модуля — `filter.modules`;
- полный путь теста вида `Модуль.Тест` или `Модуль.Тест.Контекст` — `filter.tests`;
- для наборов, тегов и контекстов используй соответственно `suites`, `tags`, `contexts`;
- при неоднозначном аргументе сначала уточни тип фильтра, не угадывай.

Для разработки сначала запускай изменённый модуль или тест, затем — согласованный более широкий набор. Не объявляй задачу проверенной только по узкому тесту, если изменение влияет на другие сценарии.

### 6.9. Запуск 1С и ожидание результата

Прочитай `.opencode/skills/db-run/SKILL.md`. Запускай назначенную тестовую базу штатным скриптом `db-run`, передавая:

```text
-CParam "RunUnitTests=<абсолютный путь к config.json>"
```

Это соответствует официальному запуску предприятия с параметром:

```text
/C"RunUnitTests=<абсолютный путь к config.json>"
```

`db-run` запускает 1С в фоне и возвращает управление сразу. Код завершения скрипта `db-run` **не является результатом тестов**.

После запуска:

1. Запомни время старта и каталог текущего прогона.
2. Ожидай появления `exit-code.txt` с ограниченным таймаутом. По умолчанию используй 10 минут, если пользователь или проект не задал другое значение.
3. Проверяй только файлы уникального каталога текущего прогона.
4. Если таймаут истёк, проверь `tests.log` и наличие процесса 1С, запущенного этим прогоном. Не запускай второй прогон поверх первого и не завершай чужие процессы.

### 6.10. Проверка результатов

Прогон считается успешным только при одновременном выполнении условий:

- `exit-code.txt` создан текущим запуском;
- файл содержит `0`;
- свежий `report.xml` существует и корректно разбирается как XML;
- суммарные значения jUnit `failures` и `errors` равны нулю;
- количество выполненных тестов больше нуля, если нулевой прогон не был явно ожидаем.

Значение `1` в `exit-code.txt` означает ошибки тестов. Отсутствие exit-code или отчёта означает незавершённый либо инфраструктурно ошибочный запуск, а не успех.

При неуспехе сообщи:

- число tests, failures, errors и skipped;
- модуль/класс и имя каждого упавшего теста;
- текст failure/error и релевантный stack trace;
- путь к `report.xml`;
- путь к полному `tests.log`;
- инфраструктурную причину, если тесты не стартовали.

Не делай вывод «тесты прошли» только по открытию 1С, отсутствию исключения в shell или существованию старого отчёта.

## 8. MCP BSL Language Server

Используй встроенный MCP-режим самого BSL Language Server:

- релизы: <https://github.com/1c-syntax/bsl-language-server/releases>;
- документация MCP-режима: <https://1c-syntax.github.io/bsl-language-server/features/McpMode/>.

BSL Language Server запускается OpenCode напрямую по stdio. Отдельный фоновый процесс и сетевой порт для этого MCP не нужны.

### 8.1. Поиск существующей установки

Сначала проверь объект `mcp.servers.bsl-language-server` в существующем `opencode.jsonc`:

1. Получи первый элемент `command` — абсолютный путь к `bsl-language-server.exe`.
2. Проверь, что файл существует и запускается.
3. Определи версию через `bsl-language-server.exe --version`, если этот параметр поддерживается текущим релизом. Если нет — используй `--help` и сведения о каталоге установки.
4. Если установлен актуальный релиз, не скачивай его повторно.
5. Если версия устарела, предложи обновление и не заменяй работающую установку без подтверждения.

Не считай любой найденный в `PATH` файл подходящей установкой: зафиксируй точный абсолютный путь, который будет использовать OpenCode.

### 8.2. Получение релиза

Если подходящей установки нет или пользователь подтвердил обновление:

1. Получи последний стабильный, не draft и не prerelease релиз через GitHub API:

   ```text
   https://api.github.com/repos/1c-syntax/bsl-language-server/releases/latest
   ```

2. Выбери asset с точным именем:

   ```text
   bsl-language-server_win.zip
   ```

3. Не подменяй его JAR, архивом для другой ОС или исходниками.
4. Скачай ZIP во временный или игнорируемый каталог, например `build/bsl-language-server/`.
5. Если GitHub API публикует `digest`, проверь SHA-256 архива.

### 8.3. Выбор каталога и распаковка

Обязательно спроси пользователя, куда распаковать BSL Language Server. Не выбирай постоянный каталог молча.

Рекомендуй версионный путь вне Git-проекта, например:

```text
C:\bsl-language-server\bsl-language-server.exe
```

Допускается выбранный пользователем каталог внутри проекта, но тогда добавь его точный относительный путь в `.gitignore`. Не добавляй слишком широкий шаблон.

Правила распаковки:

- не распаковывай поверх непустого каталога другой версии;
- сначала распакуй в новый staging-каталог;
- проверь целостность распаковки;
- найди `bsl-language-server.exe` внутри распакованного дерева;
- не перемещай только EXE отдельно: сохрани все соседние файлы поставки;
- после проверки перемести staging-каталог в согласованное место;
- проверь запуск EXE с `--help` или `--version`;
- сохрани абсолютный путь к EXE с фактическим регистром и без неоднозначных относительных сегментов.

Если в выбранном каталоге уже находится тот же релиз и исправный EXE, пропусти скачивание и распаковку.

### 8.4. Запуск в MCP-режиме

OpenCode должен запускать исполняемый файл с аргументами:

```powershell
& "<абсолютный путь>\bsl-language-server.exe" mcp --protocol stdio
```

`stdio` — локальный MCP-транспорт: OpenCode управляет жизненным циклом процесса. Не запускай отдельную фоновую копию BSL Language Server, не выбирай порт и не настраивай HTTP endpoint.

Корень текущего проекта передаётся серверу через MCP roots. Он должен охватывать основную конфигурацию и соседние каталоги расширений. Если в проекте есть `.bsl-language-server.json`, сохрани его и используй как проектную конфигурацию анализатора; не создавай настройки диагностик без запроса пользователя.

### 8.5. Доступные инструменты

Не используй имена инструментов из сторонних MCP-обёрток. Ориентируйся на фактический каталог tools подключённой версии BSL Language Server и актуальную документацию. Основные инструменты встроенного MCP:

| Инструмент | Назначение |
|---|---|
| `analyze_file` | Диагностики указанного BSL-файла |
| `document_symbols` | Методы, области и переменные файла |
| `find_references` | Ссылки на символ в позиции |
| `call_hierarchy` | Входящие и исходящие вызовы метода в позиции |
| `hover` | Сигнатура, тип и документация символа |
| `definition` | Переход к определению |
| `type_info` | Сведения о типе платформы и его членах |
| `global_member_info` | Сведения о глобальной функции, свойстве или перечислении |
| `global_member_search` | Поиск по глобальному контексту |
| `type_at_position` | Выведенный тип выражения в позиции |

Позиции `line` и `character` нумеруются с нуля.

### 8.6. Настройка OpenCode V2

Используй проектный `opencode.jsonc` в корне проекта. Не помещай серверные настройки OpenCode в `cli.json`.

Если файла нет — создай. Если существует — сохрани все посторонние настройки. Добавь `$schema` при его отсутствии и точечно обновляй только объект `mcp.servers.bsl-language-server`.

Путь к `bsl-language-server.exe` запиши абсолютным. В JSONC на Windows предпочтительны прямые слеши (`C:/Tools/.../bsl-language-server.exe`), чтобы не ошибиться с экранированием обратных слешей.

Требуемая структура:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "bsl-language-server": {
        "type": "local",
        "command": [
          "C:/<согласованный путь>/bsl-language-server.exe",
          "mcp",
          "--protocol",
          "stdio"
        ],
        "cwd": ".",
        "timeout": {
          "startup": 120000,
          "catalog": 60000,
          "execution": 600000
        }
      }
    }
  }
}
```

Правила слияния:

- не заменяй весь `mcp`;
- не удаляй другие MCP servers;
- при повторном запуске обновляй существующий `bsl-language-server`, не создавай дубликаты;
- используй синтаксис OpenCode V2: серверы находятся в `mcp.servers`;
- для BSL Language Server используй `type: "local"`, а не HTTP URL;
- не добавляй `oauth` и сетевой порт серверу, работающему по stdio.

Проверь конфигурацию:

```powershell
opencode mcp list
```

Для `bsl-language-server` ожидается состояние `connected`.

Для проверки BSL MCP выбери существующий небольшой `.bsl`-файл основной конфигурации, вызови `document_symbols`, затем `analyze_file`. Успешный ответ подтверждает запуск EXE, передачу MCP root и доступ к исходникам. При первой обработке крупного проекта анализ может занять больше времени; не запускай параллельно несколько экземпляров сервера.

## 9. Создание правил проекта `AGENTS.md`

### 9.1. Сбор данных

`AGENTS-EXAMPLE.md` из комплекта `ai-stand-setup` — канонический шаблон правил. Используй файл, расположенный рядом с исходным `AI_STAND_SETUP.md`, и перед созданием или актуализацией `AGENTS.md` прочитай его полностью. Не копируй `AGENTS-EXAMPLE.md` в корень целевого проекта.

Если рядом с исходной инструкцией шаблона нет, запроси путь к checkout той же версии `ai-stand-setup`. Не реконструируй файл по памяти и не используй шаблон от другой версии без проверки различий. Если `AGENTS-EXAMPLE.md` уже существовал в целевом проекте до запуска, не изменяй и не удаляй его.

Правила использования примера:

- исходный `AGENTS-EXAMPLE.md` используй только для чтения и не изменяй при подготовке проекта;
- в итоговом `AGENTS.md` замени placeholders фактическими значениями проекта и удали неприменимые пункты;

Перед формированием правил задай пользователю вопрос:

> Разрешены ли прямые изменения основной конфигурации, или она является типовой/read-only и все доработки должны выполняться в расширении?

Запиши ответ в `AGENTS.md` с фактическими путями.

Если `AGENTS.md` уже существует:

- прочитай его полностью;
- не удаляй пользовательские правила;
- устрани явные противоречия только после согласования;
- добавь либо актуализируй отдельный управляемый раздел для 1С;
- не создавай второй дублирующий набор правил.

### 9.2. Формирование и проверка правил

Сформируй только `AGENTS.md`, используя канонический `AGENTS-EXAMPLE.md` из исходного комплекта:

1. Замени placeholders фактическими именами и относительными путями XML-компонентов.
2. Зафиксируй согласованные границы изменения основной конфигурации и расширений.
3. Удали необязательные разделы и пункты, которые не относятся к проекту. В частности, не оставляй правила YAxUnit, если тестовый контур не выбран.
4. Добавь известные проектные команды проверки. Не придумывай несуществующие команды.
5. Не переноси в `AGENTS.md` локальные пути к базам, server/ref, пользователей, пароли, конкретные `databases[].id` и другие индивидуальные aliases.
6. Сохрани маршрутизацию `.opencode/rules`: каждый установленный файл правил должен иметь прямой маршрут с условием загрузки; не заменяй маршрутизацию безусловной загрузкой всех правил.

После формирования проверь, что в `AGENTS.md`:

- нет незаменённых placeholders и взаимоисключающих правил;
- указаны все фактические XML-компоненты проекта;
- сохранены ранее существовавшие пользовательские правила;
- необязательные разделы соответствуют реально настроенным компонентам;
- каждый файл `.opencode/rules/*.md` достижим по прямому маршруту из `AGENTS.md` или команды;
- отсутствуют секреты и локальные реквизиты информационных баз.

## 10. Финальная проверка

Выполни проверки в следующем порядке:

1. Повторно найди все `Configuration.xml`, классифицируй их через XML parser и проверь размещение основной конфигурации и расширений по разделу 4.4.
2. Проверь project skills и `bsp`.
3. Проверь комплект правил и команд по `content/manifest.json`: все целевые файлы существуют, их SHA-256 совпадают с manifest и `.opencode/.dev-agent-content.json`, OpenCode обнаруживает команду `/yaxunit-test`.
4. Проверь `.gitattributes`, `.gitignore` и отсутствие дублирующих управляемых блоков. Через `git check-ignore -v` убедись, что локальные и сгенерированные файлы игнорируются, а требуемые проектные файлы имеют ожидаемый статус.
5. Проверь, что установка не создала и не изменила `AGENTS-EXAMPLE.md` в целевом проекте, а `AGENTS.md` прошёл критерии раздела 9.2.
6. Если выбран тестовый контур, проверь единственность alias `yaxunit-test`, границы разрешения на восстановление только `YAxUnit` и `tests`, а также отключение безопасного режима, защиты от опасных действий и использования основных ролей для всех пользователей у обоих расширений.
7. Проверь существование и версию `bsl-language-server.exe`, выполни `opencode mcp list`, затем вызови `document_symbols` и `analyze_file` на существующем небольшом `.bsl`-файле.
8. Если в `tests` уже есть настоящий тест, выполни один контролируемый прогон через `/yaxunit-test` и проверь exit-code, jUnit и лог. Не создавай демонстрационный тест ради этой проверки.
9. Проверь, что все временные checkout, созданные текущим запуском, удалены. При ошибке очистки сообщи точный оставшийся путь.
10. Проверь `git status --short` и убедись, что секреты и вложенные Git-репозитории не подготовлены к коммиту.

### 10.1. Первый коммит

Только если репозиторий создан текущим запуском или пользователь подтвердил создание первого коммита в репозитории без истории:

1. Проверь `git status`.
2. Покажи пользователю состав будущего коммита.
3. Проверь отсутствие паролей, токенов, `.v8-project.json`, `.env`, EPF/CFE и vendor checkout.
4. Проверь наличие Git `user.name` и `user.email`; если их нет, попроси пользователя настроить значения.
5. Выполни:

   ```powershell
   git add .
   git commit -m "init commit"
   ```

Если после `git add` обнаружились нежелательные файлы, не коммить их; безопасно убери только эти пути из индекса без удаления рабочих файлов и исправь `.gitignore`.
