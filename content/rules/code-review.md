# Ревью кода и архитектуры

Применять только при явном запросе на ревью. До начала получить точный scope: diff, список файлов или готовое архитектурное решение. Если scope отсутствует или неоднозначен, уточнить его; не угадывать состав изменений по рабочему дереву.

## Маршрутизация

- Ревью кода или diff — прочитать зависимости из frontmatter и дополнительные правила по виду артефактов согласно корневому `AGENTS.md`; для BSL — `coding-standards.md`. Из `verification.md` применять режим ревью: только анализ и фиксация результатов.
- Ревью добавленных или измененных метаданны — прочитать `.opencode/rules/architecture.md`; `.opencode/rules/source-search.md` и правила артефактов загружать только для проверки решения по фактическим исходникам.
- Если scope совмещает оба вида ревью, объединить маршруты. Остальные правила не загружать.

## Ограничения

- Работать только для чтения и ничего не изменять в рамках ревью.
- Для отдельного ревью использовать агента `onec-reviewer`. Передать точный scope и diff: его shell, запись и запуск других агентов запрещены. Недоступный validator отметить как `не проверено — причина`, а не выполнять через обход ограничений.
- Инструменты использовать только для подтверждения фактов.
- Для кода проверять функциональные ошибки, контексты, `NULL`/`Неопределено`, транзакции, безопасность, производительность и регрессии API.
- Для архитектуры проверять границы компонентов, модель данных, интеграции, права, конкурентность, совместимость, тестируемость и rollback.
- Не включать предположения с низкой уверенностью в findings; перечислять их как проверочные вопросы или остаточные риски.

## Что включать в замечания

- Репортить подтверждённую ошибку и объяснять наблюдаемое последствие с `path:line` или ссылкой на компонент решения.
- Имена и форматирование отмечать, если нарушено явное правило проекта, сломан контракт/маршрут или существенно затруднено понимание изменённой логики. Косметические предпочтения и несвязанный старый код не включать.
- Не ревьюить сгенерированный/vendor-код, исходники YAxUnit, локальные настройки и артефакты сборки, если они не входят в scope; при необходимости зависимости прочитать и указать границы вывода.
- Не требовать новую архитектуру и тесты вне задачи только ради общего улучшения. Недостающую проверку, необходимую для вывода, оформить как следующий шаг.

## Формат результата

```markdown
## Результат ревью
**Область:** ...
**Решение:** одобрено / есть замечания / блокирующие замечания

### блокирующее|критичное|важное|незначительное — Заголовок
**Место:** `path:line` или компонент
**Уверенность:** высокая/средняя
**Доказательство:** ...
**Последствие:** ...
**Исправление / следующая проверка:** ...

## Остаточные риски
- ...
```

Определения серьёзности, решения ревью и статусов проверок — в `.opencode/glossary.md`. Непроведённые проверки не позволяют утверждать полную готовность решения.
