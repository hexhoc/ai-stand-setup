# Формы

## Подготовка

- Для `Form.xml` загрузить skill по операции: `form-info` — анализ; `form-edit`/`form-compile`/`form-add` — изменение или создание; `form-validate` — проверка.
- Для `Form.Module.bsl` применять правила BSL-разработки и `analyze_file`, включая разделы «Клиент и сервер» и «Надёжность и безопасность» из `coding-standards.md`. Бизнес-логику размещать по `architecture.md` и `coding-standards.md`.
- В существующей форме следовать её компоновке; для новой загрузить `form-patterns` и выбрать архетип до добавления элементов: форма объекта, списка, обработки, элемента справочника или пошаговый помощник.
- Обычную форму `Ext/Form.bin` не редактировать как XML. Если специализированного инструмента нет, описать точные действия в Конфигураторе и сообщить ограничение.

## Данные и обработчики

- Перед добавлением обработчика проверить событие элемента и существующую связь в XML. Связанный обработчик должен существовать в модуле ровно один раз; директива и сигнатура должны соответствовать событию. Не добавлять обязательные параметры сверх передаваемых платформой.
- Различать события формы и объекта: например, `ПослеЗаписи` формы и `ПриЗаписи` объекта имеют разные контексты и транзакционные границы.
- Поля объекта привязывать через основной реквизит `Объект.<Имя>` или `Запись.<Имя>`. Не создавать одноимённый плоский реквизит формы, значение которого не попадёт в объект при записи.
- Для преобразования данных формы в экземпляры объектов использовать `ДанныеФормыВЗначение()`/`ЗначениеВДанныеФормы()`. Методы `РеквизитФормыВЗначение()`/`ЗначениеВРеквизитФормы()` вызывать только на сервере с контекстом формы.
- Не дублировать собственными командами стандартные команды записи и проведения объектной формы.
- Не использовать для локальных переменных имена системных свойств формы: `ПараметрыВыбора`, `СвязиПараметровВыбора`, `СписокВыбора`, `ПараметрыОтбора`, `ОтборСтрок`.

## Компоновка новой формы

- Для группы страниц использовать тип `PagesGroupExtInfo`; в `Page` указывать `<enabled>true</enabled>`, если страница не отключена намеренно. Точный формат подтвердить по версии выгрузки и `form-validate`.
- Отделять реквизиты шапки от таблиц. Несколько таблиц размещать на отдельных страницах, кроме сценариев с одновременным отображением.
- Элементы располагать по частоте и последовательности работы пользователя. Дополнительные параметры не должны вытеснять основное действие формы.
- Не создавать собственную командную панель без необходимости. Команда, изменяющая хранимые данные, должна быть соответствующим образом помечена в метаданных.
- Обязательность ввода задавать свойством проверки заполнения реквизита, а не только клиентской проверкой перед нажатием кнопки.

## Асинхронность

- Не использовать модальные окна и синхронные диалоги (`Вопрос`, `Предупреждение`, `ВвестиЗначение` и аналоги). Выбирать асинхронный вариант, доступный на минимальной платформе и при режиме совместимости проекта.
- Перед использованием `Асинх`/`Ждать` проверить поддержку платформой и клиентом: платформа 8.3.18+. Если поддержки нет, использовать `ОписаниеОповещения`: экспортную клиентскую процедуру с параметрами операции. Для обычного результата диалога — `(Результат, ДополнительныеПараметры)`; для остальных оповещений сигнатуру проверять отдельно.
- Обработчик формы с `Асинх` не приостанавливает завершение платформенного события сам по себе. Не использовать его там, где платформа должна дождаться решения до закрытия, записи или отмены действия, без подтверждённого шаблона этого события.

## Проверка формы

- После изменения проверить соответствие событий XML и обработчиков модуля в обе стороны, включая команды и директивы компиляции.
- Структурная валидация XML не доказывает, что форма открывается и сценарий работает; платформенную или UI-проверку отмечать отдельно.
- Временные сообщения, тестовые значения и диагностические элементы удалить до завершения работы.
