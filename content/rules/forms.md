# Формы

1. Для работы с `Form.xml` обязательно загружать соответствующий skill: `form-info` — для анализа, `form-edit`/`form-compile`/`form-add` — для изменения или создания, `form-validate` — для проверки.
2. `Form.Module.bsl` — обычная BSL-разработка с `analyze_file`.
3. Перед добавлением обработчика проверить событие элемента и существующую связь в XML. Связанный обработчик существует в модуле ровно один раз, а его директива и сигнатура соответствуют событию; не добавлять обязательные параметры сверх передаваемых платформой.
4. Поля объекта привязывать через основной реквизит `Объект.<Имя>` или `Запись.<Имя>`; не создавать одноимённый плоский реквизит формы, значение которого не попадёт в объект при записи.
5. Для преобразования данных формы и прикладных объектов использовать `ДанныеФормыВЗначение()`/`ЗначениеВДанныеФормы()`. Методы `РеквизитФормыВЗначение()`/`ЗначениеВРеквизитФормы()` вызывать только на сервере с контекстом формы.
6. Не передавать изменяемый объект, набор записей или таблицу значений в `ЗначениеЗаполнено()`; проверять ссылку, конкретный реквизит либо состояние `ЭтоНовый()`.
7. Не дублировать собственными командами стандартные команды записи и проведения объектной формы. Размещение бизнес-логики — по `architecture.md` и `coding-standards.md`.
8. Не использовать локальные переменные с именами системных свойств формы: `ПараметрыВыбора`, `СвязиПараметровВыбора`, `СписокВыбора`, `ПараметрыОтбора`, `ОтборСтрок`.
9. Размещение элементов следует существующей форме; для новой формы загрузить skill `form-patterns`.

## Клиент, сервер и права

При изменении BSL применять разделы «Клиент и сервер» и «Надёжность и безопасность» из `coding-standards.md`. В XML проверить доступность команд и элементов для целевых ролей; скрытие элемента не заменяет серверную проверку прав.

## Компоновка новой формы

- Выбрать архетип до добавления элементов: форма объекта, списка, обработки, элемента справочника или пошаговый помощник.
- Для группы страниц используется тип `PagesGroupExtInfo`; элемент `Page` содержит `<enabled>true</enabled>`, если страница не отключена намеренно. Точный формат подтвердить по версии выгрузки и `form-validate`.
- Отделять реквизиты шапки от таблиц. Для нескольких таблиц использовать отдельные страницы, если одновременное отображение не является частью сценария.
- Имена групп, элементов, команд и обработчиков должны быть стабильными и предметными; пользовательское представление задаётся заголовком, а не техническим именем.
- Элементы располагать по частоте и последовательности работы пользователя. Дополнительные параметры не должны вытеснять основное действие формы.
- Не создавать собственную командную панель без необходимости. Команда, изменяющая хранимые данные, должна быть соответствующим образом помечена в метаданных.
- Обязательность ввода задавать свойством проверки заполнения реквизита, а не только клиентской проверкой перед нажатием кнопки.

## События и асинхронность

- По [#std703](https://v8std.ru/std/703/) не использовать модальные окна и синхронные диалоги (`Вопрос`, `Предупреждение`, `ВвестиЗначение` и аналоги). Выбирать асинхронный вариант, доступный на минимальной платформе и при режиме совместимости проекта.
- Для `Асинх`/`Ждать` проверить поддержку платформой и клиентом (платформа 8.3.18 и новее с подходящим режимом совместимости). Если этот вариант недоступен, использовать `ОписаниеОповещения`: обработчик — экспортная клиентская процедура с параметрами, соответствующими операции; для обычного результата диалога — `(Результат, ДополнительныеПараметры)`. Универсальную сигнатуру не переносить на все оповещения без проверки.
- Не путать события формы с событиями объекта: например, `ПослеЗаписи` формы и `ПриЗаписи` объекта имеют разные контексты и транзакционные границы.
- Обработчик формы с `Асинх` не приостанавливает завершение платформенного события сам по себе. Не использовать его там, где платформа должна дождаться решения до закрытия, записи или отмены действия, без подтверждённого шаблона этого события.
- Результат асинхронного метода получать через `Ждать`, если от него зависит продолжение сценария. Иначе исключение и завершение операции могут остаться необработанными.
- После `Ждать` учитывать, что форма могла быть закрыта, текущая строка изменена, а данные — устареть.
- Не смешивать старую схему оповещений и `Асинх`/`Ждать` в одной цепочке без явной границы адаптера и проверки минимальной версии платформы.
- Для обоих способов определить завершение, обработку исключения, отмену и поведение при закрытии формы до получения результата. Серверная проверка допустимости операции остаётся обязательной независимо от клиентского сценария.

## Проверка формы
- 
- После изменения проверить соответствие событий XML и обработчиков модуля в обе стороны, включая команды и директивы компиляции.
- Структурная валидация XML не доказывает, что форма открывается и сценарий работает; платформенную или UI-проверку отмечать отдельно.
- Временные сообщения, тестовые значения и диагностические элементы удалить до завершения работы.

Обычная форма `Ext/Form.bin` не редактируется как XML. Без специализированного инструмента описать точные действия в Конфигураторе и сообщить ограничение.
