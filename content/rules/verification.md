# Проверка изменений

Проверяется последнее сохранённое состояние. Содержательная правка делает относящийся к ней результат устаревшим. Не повторять проверку неизменённого содержимого без новой причины. Статусы всех уровней — по `.opencode/glossary.md`.

## Режим работы

- При реализации исправлять относящиеся к задаче диагностики и проверять результат после исправления.
- При ревью только читать и анализировать: не исправлять, не форматировать, не загружать исходники в базу и не менять окружение. Ограничения агента имеют приоритет над рекомендацией запустить инструмент; недоступная проверка получает статус `не проверено — причина`.

## BSL

Для каждого изменённого `.bsl`:

1. Вызвать `analyze_file` после последней правки.
2. Обработать синтаксические ошибки и связанные с изменением диагностики важности `BLOCKER`, `CRITICAL`, `MAJOR` в изменённых строках или затронутом пути. Несвязанные старые диагностики не исправлять попутно; остальные перечислить с решением/обоснованием.
3. Не путать важность диагностики BSL LS с числом LSP severity. Если MCP возвращает только LSP severity, отдельно обработать все ошибки, а важность прочих подтвердить по метаданным диагностики; неизвестную важность явно отметить.
4. После исправления повторить анализ затронутого файла. Новые относящиеся к изменению ошибки также устранить и проверить; не ограничивать число итераций ценой незамеченной ошибки.
5. Проверить литералы `\t`, `\n`, `\r` по `coding-standards.md`.
6. Для изменённого экспортного метода проверить `find_references`; при изменении сигнатуры, результата, побочных эффектов или отказа обязательно проверить `call_hierarchy` и динамические точки входа по `source-search.md`.

`analyze_file` не является компиляцией платформой и не доказывает бизнес-корректность. При недоступности сервера выполнить доступные проверки и явно отметить непроведённый анализ.

Анализ влияния нужен также при удалении/переименовании, изменении подписки, задания, RLS и транзакционного пути. Проверить прямые, строковые и платформенные точки вызова.

## XML и метаданные

- Загрузить профильный skill: `meta-validate`, `form-validate`, `role-validate`, `skd-validate`, `mxl-validate`, `subsystem-validate`, `interface-validate`, `xdto-validate`, `cfe-validate`, `cf-validate`, `erf-validate` или `epf-validate`.
- Расширение проверять вместе с точной основной конфигурацией.
- Проверить регистрацию объекта в родительских XML, права, включение в подсистему и командный интерфейс по `metadata.md`, если они затронуты. Для неприменимого пункта указать причину.
- Не считать визуально корректный XML прошедшим проверку. После последующей XML-правки повторить профильную проверку.
- Для формы различать корректность XML, открытие платформой и пользовательский сценарий; для отчёта/печати — структуру и фактический результат.

## Необязательный платформенный контроль

Предложить, когда изменены директивы компиляции, вызовы платформенного API, заимствования расширения либо статический анализ не снимает сомнение. Перед подключением к dev-базе получить подтверждение состава операции и проверить, что проверяется последняя версия исходников; отдельную загрузку согласовать по `AGENTS.md`.

- Для расширения — skill `db-cfe-admin`, операция `check`, параметры `-Name <имя> -Checks modules` и нужные контексты компиляции. Проверку применимости (`apply`) учитывать отдельно.
- `db-cfe-admin check` не проверяет основную конфигурацию. Для неё использовать синтаксический контроль Конфигуратора с параметрами, подтверждёнными документацией установленной платформы; при отсутствии подходящего skill описать точное ручное действие и критерий результата.
- Сохранить код завершения, лог, проверенные контексты, версию платформы и соответствие исходникам. Успех на сервере не доказывает компиляцию веб-клиента.

## Поведение и отчёт

Разрешение на создание/запуск тестов — в `AGENTS.md`, организация тестов — в `testing.md`. Для исправления ошибки повторить исходный сценарий, если разрешена соответствующая runtime-проверка. Статический анализ, компиляция и runtime — отдельные уровни.

Для каждой проверки указать инструмент, артефакт/сценарий, контекст и результат: `проверено`, `ошибка` или `не проверено — причина`. Не утверждать «всё проверено», если часть применимых уровней отсутствовала.
