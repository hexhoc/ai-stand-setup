# Отчёты и СКД

- До изменения определить источник, требуемые строки, параметры/период, вычисляемые поля, ресурсы, группировки, отборы, варианты и пользовательские настройки. Учесть пустой результат, дубли и итоговые строки.
- Прочитать схему через `skd-info`, изменять через `skd-edit` или `skd-compile`, проверить `skd-validate`. Не пересоздавать всю схему ради локальной правки и не сбрасывать пользовательские варианты без задачи.
- Поля запроса, типы параметров и доступные метаданные подтвердить по источникам. Проектирование и оптимизация запросов — по `query-design.md`.
- Вычисления, влияющие на отбор/группировку больших данных, по возможности выполнять источником. Не суммировать выражение повторно на разных уровнях итогов без проверки смысла ресурса.
- Проверить доступность полей при RLS, функциональных опциях и нужных ролях; скрытое поле не означает запрет чтения. Изменение прав — по `access-rights.md`.
- Для отчёта с `РАЗРЕШЕННЫЕ` подтвердить по `query-design.md`, что детализация и итоги должны отражать только доступную пользователю область данных. Если требуется полнота данных, не маскировать недостаток прав неполным результатом.
- Для нового объекта отчёта применить маршрут метаданных; для макета печати — маршрут `printing.md`.

## Внешний отчёт

Для нового ERF загрузить `erf-init`, для сборки — `erf-build`, для выгрузки — `erf-dump`, для проверки — `erf-validate`. При регистрации в БСП загрузить `bsp` и проверить API соответствующей версии; не считать регистрацию внутреннего отчёта и внешнего ERF одинаковой.

Сборку выполнять на согласованной базе с нужными ссылочными типами; выгрузка из пустой базы может потерять типы. Сам факт сборки ERF не доказывает правильность итогов.

## Проверка результата

Структуру схемы, компиляцию и формирование отчёта учитывать раздельно. Для разрешённого runtime-сценария сверить детализацию/итоги на известных данных, пустой период, параметры, варианты и целевую роль. Запрос на тесты и их состав — по `AGENTS.md`; статусы — по `.opencode/glossary.md`.
