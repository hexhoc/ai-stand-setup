# Стандарты разработки

Применять вместе с локальным стилем изменяемого модуля.

**Источник стандартов.** Ссылки вида `#std783` — номера стандартов разработки 1С. Текст стандарта: `https://v8std.ru/std/<номер>/`. Страница диагностики BSL LS: `https://v8std.ru/diagnostics/bslls/<Имя>/` ведёт к связанному стандарту.

## Форматирование

- Сохранять форматирование и регионы существующего модуля; не переформатировать несвязанный код.
- Один оператор размещать на строке. Длинное выражение переносить по смысловым частям, сохраняя читаемую вложенность.
- Многострочные строки продолжаются `|` и пробелами; текстовые `\t`, `\n`, `\r` не являются BSL escape-последовательностями.
- Не выравнивать большие блоки пробелами так, чтобы изменение одного имени требовало переформатирования соседних строк.

## Имена и API

- Не использовать магические строки и числа, если у значения есть устойчивый предметный смысл.
- Имя временной переменной должно отражать содержимое или этап алгоритма
- В идентификаторах использовать `е`, а не `ё`; пользовательский текст сохраняет нормативное написание.
- Не менять сигнатуру, тип результата или наблюдаемое поведение экспортного метода без проверки вызывающих.
- Публичный метод имеет не более семи параметров. При превышении порога передавать структуру параметров.

### Поиск существующей реализации

Перед созданием вспомогательного метода (#std440):

1. Найти существующую реализацию, в том числе командой `rg -i "<ключевое слово>" --glob "**/CommonModules/**/*.bsl"`.
2. Проверить библиотеки проекта. Для БСП проверить как минимум `ОбщегоНазначения`, `ОбщегоНазначенияКлиентСервер`, `СтроковыеФункцииКлиентСервер`.
3. Создавать новый универсальный метод только при наличии минимум двух реальных вызовов в текущей задаче. Иначе оставлять метод локальным.


### Документирующий комментарий

Пример:

```bsl
// Возвращает описание настройки по имени.
//
// Параметры:
//  ИмяНастройки - Строка - Имя получаемой настройки.
//
// Возвращаемое значение:
//  Структура - Описание настройки.
//
Функция ОписаниеНастройки(ИмяНастройки) Экспорт
```

## Методы и условия

- Процедура или функция решает одну задачу. Предусловия проверять в начале ранним выходом, если это не скрывает основную ветку.
- Максимальная вложенность условий и циклов — три уровня. При превышении выносить самостоятельную часть в отдельный метод.
- Параметры располагать от обязательных к необязательным. Не использовать длинный набор булевых параметров вместо структуры настроек или нескольких предметных методов.
- Не сравнивать булево значение с `Истина` или `Ложь`, если прямое условие читается однозначно.
- Избегать отрицательных условий и «йода»-сравнений, если они ухудшают предметное чтение кода.
- Не использовать тернарный оператор для ветвей с побочными эффектами или сложной логикой.

## Клиент и сервер

- Клиент не выполняет запросы и тяжёлую обработку данных; минимизировать клиент-серверные переходы и размер передаваемых значений.
- `&НаСервереБезКонтекста` предпочтительнее, если данные формы не нужны. Не применять директиву механически: используемые методы и значения должны быть доступны в выбранном контексте.
- Не размещать бизнес-логику записи и проведения в форме.

## Данные, запросы и производительность

- Запросы параметризуются; подзапрос в списке полей и коррелированный подзапрос требуют переработки.
- Массовая обработка использует пакетные запросы и наборы записей, а не запись элемента за элементом без необходимости (#std436, #std654). В теле цикла по данным запрещены `Запрос.Выполнить()`, обращение к реквизитам ссылки через точку и чтение реквизита объекта по ссылке.
- Результат запроса сохранять в отдельную переменную, если он используется далее или код должен различать выполнение запроса и выборку.
- Для коллекции выбирать алгоритм по объёму и частоте поиска: повторный линейный поиск внутри цикла заменять соответствием, индексом либо пакетной выборкой.
- Кэшировать только данные с понятным временем жизни и способом инвалидирования.
- Не получать объект целиком ради чтения одного-двух реквизитов (#std496). Несколько реквизитов читать одним запросом. В проекте на БСП использовать `ОбщегоНазначения.ЗначенияРеквизитовОбъектов(...)`, предварительно проверив наличие метода в версии БСП проекта.
- В рамках одной операции набор записей в один регистр записывать один раз, а не построчно в цикле (#std792).

```bsl
// Плохо: скрытый запрос к базе на каждой итерации.
Для Каждого Строка Из Объект.Товары Цикл
	Вес = Строка.Номенклатура.Вес;
КонецЦикла;

// Хорошо: один запрос на все ссылки.
Запрос = Новый Запрос(
"ВЫБРАТЬ
|	Номенклатура.Ссылка КАК Ссылка,
|	Номенклатура.Вес КАК Вес
|ИЗ
|	Справочник.Номенклатура КАК Номенклатура
|ГДЕ
|	Номенклатура.Ссылка В(&Ссылки)");
Запрос.УстановитьПараметр("Ссылки", Объект.Товары.ВыгрузитьКолонку("Номенклатура"));

Веса = Новый Соответствие;
Выборка = Запрос.Выполнить().Выбрать();
Пока Выборка.Следующий() Цикл
	Веса.Вставить(Выборка.Ссылка, Выборка.Вес);
КонецЦикла;
```

## Обработчики записи и обмен

В обработчиках `ПередЗаписью`, `ПриЗаписи`, `ПередУдалением` и в подписках на эти события сначала проверять `ОбменДанными.Загрузка` (#std773, #std464, #std465, #std752). При обмене объект должен загружаться как есть, без дополнительных проверок и действий.

```bsl
Процедура ПередЗаписью(Отказ)

	Если ОбменДанными.Загрузка Тогда
		Возврат;
	КонецЕсли;

	// Код обработчика.

КонецПроцедуры
```

Исключение — обмен, который при загрузке регистрирует изменения для выгрузки на другие узлы плана обмена. Любое другое исключение пояснять комментарием. Код, устанавливающий `ОбменДанными.Загрузка = Истина`, сам отвечает за заполнение и целостность объекта. Проверка BSL LS: `DataExchangeLoading`.

## Транзакции и конкурентность

Основа: #std783 (транзакции), #std648 (ответственное чтение), #std460 (управляемый режим блокировки), #std490 (блокировка объекта), #std659 (избыточные блокировки).

### Явная транзакция

Учитывать режим управления блокировками проекта. Блокировка в шаблоне нужна, если в транзакции выполняется ответственное чтение.

```bsl
НачатьТранзакцию(); // Вне Попытки, непосредственно перед ней.
Попытка
	Блокировка = Новый БлокировкаДанных;
	Элемент = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
	Элемент.УстановитьЗначение("Номенклатура", Номенклатура);
	Элемент.Режим = РежимБлокировкиДанных.Исключительный;

	Блокировка.Заблокировать(); // До чтения данных, на основании которых выполняется запись.

	// Чтение и запись.
	ЗафиксироватьТранзакцию();
Исключение
	ОтменитьТранзакцию(); // Первое действие в блоке Исключение.
	ЗаписьЖурналаРегистрации(НСтр("ru = 'Выполнение операции'"), УровеньЖурналаРегистрации.Ошибка, , ,
		ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	ВызватьИсключение;
КонецПопытки;
```

Все действия между `НачатьТранзакцию` и завершением транзакции — чтение, блокировка и обработка — находятся в одном блоке `Попытка`. После отмены повторно бросать исключение, иначе внешняя транзакция не будет отменена и платформа сообщит: «В данной транзакции происходила ошибка».

### Когда транзакция не нужна

- Если кроме записи объекта или набора записей ничего не требуется и ответственное чтение не нужно, не вызывать `НачатьТранзакцию`: платформа создаст транзакцию сама (#std783, п. 1.4).
- В обработчиках `ПередЗаписью`, `ПриЗаписи`, `ПередУдалением`, `ОбработкаПроведения` и подобных платформа уже открыла транзакцию. Метод, предназначенный только для вызова из такого обработчика, не открывает свою транзакцию. Если транзакция является предусловием, проверять `ТранзакцияАктивна()` и бросать исключение при вызове вне транзакции.
- Платформа не поддерживает вложенные транзакции (#std783, п. 1). Исключение внутри транзакции не отменяет её, а запрещает успешное завершение; реальная отмена происходит на `ОтменитьТранзакцию`. До отмены не обращаться к базе, в том числе неявно, например за представлением ссылки.

### Ответственное чтение

Ответственным считается чтение, по результатам которого изменяются данные или принимаются бизнес-решения (#std648).

- Выполнять ответственное чтение в транзакции и устанавливать управляемую блокировку до чтения.
- Для данных, которые будут изменены, устанавливать исключительную блокировку до чтения.
- Для данных, используемых только для чтения, например при формировании движений, применять разделяемую блокировку; для изменяемых данных — исключительную.
- Ответственное чтение не требуется для динамических списков, поиска, большинства отчётов, условно постоянных данных, монопольных сценариев обновления ИБ и первичного заполнения.


### Границы и порядок блокировок

- Внутри транзакции запрещены внешние вызовы и диалоги: `HTTPСоединение`, `WSПрокси`, `Новый COMОбъект`, вопросы пользователю и ожидания. Внешний вызов выполнять до или после транзакции, а результат фиксировать отдельной короткой транзакцией.
- Порядок блокировок должен быть единым во всех кодовых путях. Если проект не задаёт иное, блокировать ресурсы в алфавитном порядке имён объектов метаданных, внутри объекта — по возрастанию значений ключей. Порядок описывать комментарием в общем модуле, который устанавливает блокировки.
- Не блокировать регистр целиком; всегда указывать значения измерений (#std659, #std661).

## Расширения

Перед перехватом метода проверить в исходниках точной версии основной конфигурации:

1. Метод существует с таким именем.
2. Контекст `&НаСервере`, `&НаКлиенте` или `&НаСервереБезКонтекста` совпадает с оригиналом.
3. Количество и порядок параметров совпадают с оригиналом.

Сигнатуру и тело перехватываемого метода сверять с точной версией основной конфигурации. После обновления типовой конфигурации повторно сверять `&ИзменениеИКонтроль` с оригинальным телом.

- `&Перед` и `&После` не меняют контракт метода.
- Результат функции изменять через `&Вместо`, вызывая `ПродолжитьВызов(...)`, если контракт требует исходную логику.
- `&ИзменениеИКонтроль` применять только для вставки в середину метода: такое изменение наиболее чувствительно к обновлениям.
- Для всех новых имён использовать префикс расширения. Заимствовать только необходимые объекты и формы.

## Надёжность и безопасность

- Привилегированный режим минимален по области и обоснован. Не использовать его для обхода неверно спроектированных прав.
- Перехват исключения без записи в журнал и без повторного броска запрещён (#std499). Пользователю показывать `КраткоеПредставлениеОшибки`, в журнал записывать `ПодробноеПредставлениеОшибки`. Пользовательский текст не должен содержать имена методов, запросов и пути.
- Не включать пароли, токены, персональные данные и содержимое закрытых документов в код, URL и диагностические сообщения.
- `Выполнить` и `Вычислить` с внешними или пользовательскими данными запрещены (#std770, #std801, #std669). Если динамический код неизбежен, перед его вызовом включать безопасный режим и обосновывать решение в итоговом отчёте.
- Экспортный серверный метод, доступный с клиента, не доверяет входным данным: самостоятельно проверяет права и валидирует параметры (#std678, #std679). Признак `Вызов сервера` общего модуля устанавливать только при реальной необходимости.
- Значения передавать в запрос только параметрами. Не включать значения в текст запроса конкатенацией.
- Данные из внешнего, динамического или слаботипизированного источника проверять и нормализовать на границе. Внутри прикладного метода работать с одним согласованным представлением, а не повторять проверки типа в каждой ветви.
- Перед чтением необязательного свойства структуры проверять его наличие либо использовать согласованный безопасный accessor; отсутствие свойства и пустое значение не смешивать.

## Локализация

- Пользовательские строки оборачивать в `НСтр` (#std761, #std764, #std763).
- Подстановки выполнять через `СтрШаблон(НСтр("ru = '... %1'"), Значение)`, а не конкатенацией.
- Форматирование даты, числа и булева значения задавать явно через `Формат`.

## Журналирование

- Писать в журнал для диагностируемого эксплуатационного события, ошибки или явно поставленной задачи, а не как замену обработке результата.
- Категория события стабильна, именуется в формате `Подсистема.Операция` и оформляется через `НСтр` (#std498); уровень важности соответствует влиянию, а не удобству поиска.
- Диагностический контекст содержит идентификатор операции, безопасные ключи объекта, этап и номер попытки, но не сериализованный объект целиком.
- При обработке исключения сохранять исходную причину и добавлять контекст текущей операции. Не создавать несколько одинаковых записей на каждом уровне вызова.
- Не журналировать секреты, персональные данные и большие тела запросов/ответов. Не писать запись на каждую строку массовой операции без отдельной диагностической необходимости.

## Комментарии и сопровождение

- Комментарий объясняет причину, ограничение, неочевидный алгоритм или контракт, а не пересказывает строку кода.
- Комментарий публичного метода не должен обещать поведение, которого нет в реализации.
- `TODO` и `FIXME` содержат ссылку на задачу либо достаточное условие удаления временного решения.
- Не оставлять закомментированный код, временные сообщения, точки останова и неиспользуемые переменные, созданные текущей правкой.
- После правки проверить изменённый фрагмент и соседний код, влияющий на транзакцию, права, контекст выполнения и публичный контракт.
