# Интеграции 1С

Правило применяется к HTTP-/Web-сервисам, REST/SOAP-клиентам, очередям, webhook и файловому обмену.

## До реализации

- Зафиксировать контракт: направление обмена, endpoint и метод, формат и версию данных, аутентификацию, ожидаемые статусы, таймауты, идемпотентность, повторы, частичный результат и журналирование.
- Найти существующий проектный аналог по `.opencode/rules/source-search.md`; совпадение внешнего протокола не отменяет проверку предметного контракта.
- Если возможна реализация через БСП, загрузить skill `bsp`. Его справочники подтверждают БСП 3.1.11; для другой версии существование и сигнатуры API проверить по исходникам проекта.
- Для известного платформенного API использовать `type_info`, `global_member_info` или `global_member_search`. Эти инструменты подтверждают типы и члены, но не заменяют документацию по протоколу и не доказывают отсутствия неизвестного механизма.
- Метаданные сервисов изменять через `meta-*`, права — через `role-*`, XDTO-контракты — через `xdto-*`; после изменения запускать соответствующий validator.

## Реализация

- Не выполнять потенциально долгий сетевой вызов синхронно на клиенте и не удерживать транзакцию во время обращения к внешней системе.
- Использовать штатные `HTTPСоединение`/`HTTPЗапрос`, `ЧтениеJSON`/`ЗаписьJSON`, `ЧтениеXML`/`ЗаписьXML` или подтверждённый API БСП; не собирать JSON/XML конкатенацией строк.
- Формат дат, часовой пояс, точность чисел, представление булевых и пустых значений задавать контрактом. Не полагаться на локальные настройки сеанса или неявное строковое преобразование.
- XML проверять по XSD, если схема является частью контракта; отсутствие схемы не отменяет проверку обязательных узлов, пространства имён и версии формата.
- Явно задать поддерживаемые выбранным API таймауты. Не использовать бесконечное ожидание и магические значения без проектного основания.
- Проверять транспортный статус и прикладной ответ. Ошибка содержит безопасный диагностический контекст: операция, endpoint без секретов, статус и номер попытки; токены, пароли и персональные данные не журналируются.
- Повтор изменяющего запроса разрешён только при определённой идемпотентности. Повторы ограничены, имеют задержку и прекращаются на постоянной ошибке; после неизвестного результата сначала установить фактическое состояние операции.
- Секреты не хранить в коде, URL, комментариях и диагностических сообщениях. Получение и обновление токена централизовать.
- Частичный результат обрабатывать явно: принятые, отклонённые и неизвестные элементы различаются; повтор не отправляет подтверждённо обработанные данные заново.
- Для новой интеграции зафиксировать внешний владелец, версию контракта, способ аутентификации, необходимые права, точку настройки endpoint и ссылку на требования. Секретные значения в эту документацию не включать.

## Проверка

- BSL проверяется по `.opencode/rules/verification.md`, метаданные и контракты — профильными validators.
- Проверку сериализации отделять от реального сетевого вызова. Runtime-проверки, запись тестовых данных и обращение к внешнему endpoint выполнять только по явному запросу пользователя и в разрешённом тестовом контуре.
- В результате указать, что подтверждено статически, что проверено на тестовом endpoint и какие свойства внешней системы остались непроверенными.
